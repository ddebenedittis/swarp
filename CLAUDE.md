# CLAUDE.md

## Project Overview

`swarp` (Swarm + Warp) is a GPU-resident, differentiable, vectorized 2D
multi-agent simulator built on NVIDIA Warp with zero-copy PyTorch interop. Conceptually
VMAS, but the step is compiled Warp kernels instead of per-entity PyTorch ops. All state
lives on-device as `[n_envs, n_agents]` Warp arrays; the hot loop does no host↔device copies.

`VectorizedMultiAgentSimulator/` is **not** a submodule and not part of this package: it is
an optional, gitignored local VMAS clone that `swarp/benchmark/compare_vmas.py` falls back to when
`vmas` is not importable. It is ruff-excluded. Do not edit it.

## Build & Run

```bash
uv venv
uv pip install -e . --group dev
uv pip install -e '.[viz]'                 # optional: viewer/video tests stop skipping
uv run pytest                              # dynamics, gradients, neighbors, collisions, determinism
uv run pytest -m "not gpu"                 # what CI runs (no CUDA device on the runners)
python -m swarp.benchmark.throughput        # NavigationScenario hot-path env-steps/s
python -m swarp.benchmark.compare_vmas      # vs VMAS; needs `.[bench]` (pulls in vmas, numpy<2)
uv pip install --group docs                # docs toolchain (no torch/warp needed)
uv run --no-sync sphinx-build -b html -W docs docs/_build/html   # build the docs site
```

Markers declared in `pyproject.toml`: `gpu` (needs CUDA) and `viz` (needs the `viz`
extra). Benchmark numbers and the multi-venv cross-simulator setup live in
`docs/benchmarks.md` — keep them out of the README.

`docs/` is a Sphinx site (MyST Markdown + the Read the Docs theme, `docs/conf.py`), deployed
to GitHub Pages by `.github/workflows/docs.yml`. It carries **no autodoc**, so the build needs
neither torch nor warp — `uv sync --only-group docs` is the whole toolchain, and `-W` means a
dead cross-reference fails CI. The README is the presentation + install page only; anything
longer belongs in a docs page. Screenshots and the demo clip in `docs/_static/` are committed
and regenerated by `python docs/make_assets.py` (needs the `viz` extra).

`compare_vmas` takes `--metric {throughput,memory,both}`; falls back to the
`./VectorizedMultiAgentSimulator` checkout if `vmas` is not importable.

## Speed Is a First-Class Citizen

Every change that touches the step — kernels, `Stepper`, neighbors, collisions, bodies, fused scenario passes, interop — must be benchmarked before it is called done.
The procedure at the end of an implementation:

1. Record a baseline from the pre-change code (`git stash` or a checkout of the previous commit), running `python -m swarp.benchmark.throughput` on the same machine, same batch sizes, same device.
2. Run the same benchmark on the new code.
3. Report both numbers and the delta in percent, not just the new number.

The case that matters most is the **fastest configuration**, because that is the one the project's numbers are claimed on and the one users run in training loops.
Benchmark that first, and only then the slower paths:

- `use_graph=True` — whole-step CUDA graph capture (`Environment`'s `"auto"` default on CUDA, and `throughput.py`'s default, so the plain benchmark command already measures it; `--no-graph` pins it off for the eager comparison). Check `env.graph_mode` to confirm capture actually happened rather than falling back to eager persistent execution.
- `fused=True` — the scenario's fused Warp obs/reward kernels, which is what the capture folds into; without it there is no whole-step hook and no capture.
- `torch.no_grad()` — the tape-free hot path. A taped step allocates fresh per-step buffers and is a different regime entirely.
- `device="cuda:0"` and `dtype=torch.float32`.
- `clone_outputs=False` and `auto_reset=False` — both add per-step work (`auto_reset` runs `reset_world` every step over the whole batch).
- A capture-compatible `neighbor_method` (`brute` or `uniform_grid`); `hash_grid` blocks capture.

A change that leaves the eager path untouched but slows the captured path down is still a regression.

Then decide based on the result rather than filing it away: a regression beyond run-to-run noise means either fixing it or explicitly justifying the trade (correctness fix, new capability) in the commit message.
Never report an implementation as complete with an unexplained slowdown.
Cross-simulator claims use `python -m swarp.benchmark.compare_vmas`; published numbers belong in `docs/benchmarks.md`.

## Architecture

Layering (torch-facing at the top, Warp kernels at the bottom):

```
Environment          swarp/core/environment.py  VMAS-style API: reset/step/radius_graph over a Scenario
    ↓ drives
Scenario (ABC)       swarp/scenarios/base.py    make_world / reset_world / observation / *_reward
    ↓ builds
World                swarp/core/world.py        batched state tensors, goals, obstacles, RNG
    ↓ owns
Stepper              swarp/core/stepper.py      THE substep pipeline: neighbors → forces → bodies → integrate
    ↓ launches
kernels              swarp/dynamics/kernels.py, swarp/core/collisions.py, swarp/core/neighbors.py,
                     swarp/core/bodies.py, swarp/sensors/lidar_kernels.py, swarp/scenarios/*_kernels.py
```

Off to the side of that spine (all optional, none on the hot path unless asked for):
`swarp/render/` (~2.1k LOC pygame viewer: renderer/overlays/camera/hud/input/layout/video/
notebook/demo), `swarp/sensors/lidar.py` (opt-in differentiable ray-cast, torch + Warp
backends), and `swarp/interop/{compile,persistent,torchrl}.py`
(`torch.library.custom_op` for `torch.compile`, CUDA-graph capture of the no-grad step,
TorchRL `EnvBase` wrapper).

- `swarp/core/state.py` — `WorldState`: structure-of-arrays Warp storage. One unified state
  for all models (`pos/theta/vel/speed/ang_vel`); holonomic agents ignore `theta/ang_vel`.
- `swarp/core/bodies.py` — movable/compound rigid bodies. An `ObstacleKind.MOVABLE` obstacle
  is integrated **inside the substep loop** from the reaction of the same agent contacts
  `collisions.py` applies (gather-based, thread per `(env, obstacle)`, no atomics). Shapes
  sharing a body id form one compound rigid pose (Push-T's T). **Not taped**
  (`record_tape=False`), so a scenario needing gradients through a body integrates it in
  torch itself. Box-box obstacle-obstacle contacts are not modelled.
- `swarp/dynamics/base.py` — `DynamicsModel`/`ControlMode`/`Integrator` enums, `AgentConfig`
  (per-agent, mixable in one world), and `build_agent_params`. Four models: holonomic point,
  diff-drive, kinematic bicycle (all 2D), and a 6-DOF `+`-config quadrotor whose `AgentConfig`
  factory lives in `swarp/dynamics/drone.py`.
- `swarp/interop/autograd.py` — the torch↔Warp bridge: `_WarpStepFn` (a `torch.autograd.Function`
  replaying Warp adjoints in `backward`), `warp_step`, and `rollout` for BPTT over multi-step rollouts.
- `swarp/core/neighbors.py` — `NeighborGrid` with three backends (per-env brute force, a batched
  radix-sort `uniform_grid`, and one `wp.HashGrid` over all envs), selected via
  `WorldConfig.neighbor_method`; tested to agree exactly.
- `swarp/scenarios/` — 10 scenarios: navigation, flocking, formation, discovery, sampling,
  transport, pusht, giveway, shepherding, caging. Each pairs a torch implementation of
  obs/reward/done with fused Warp `*_kernels.py` for the no-grad hot path. The torch path is
  the **parity oracle** the fused kernels are tested against — keep them independent rather
  than sharing code. The first seven all reward monotone progress toward a goal; the last
  three deliberately do not (giveway requires moving *away* from your goal, caging scores an
  angular property rather than a distance, and shepherding's environment reacts).
  `giveway`/`shepherding`/`caging` each emit `info()["multiobj_reward"]`
  `[n_envs, n_agents, n_obj]` summing to the scalar reward, so a shaping imbalance is visible
  on the first training iteration rather than after an hour — that check has already caught
  one 22x imbalance.
- `swarp/scenarios/fused.py` — `FusedScenario`, which all 10 subclass. A scenario declares its
  persistent buffers as a tuple of `Buf` from `fused_spec(n_envs)` and its launch sequence
  as `launch_fused(FusedPass)`; the framework owns lazy allocation, uint8→bool reinterpret
  views, Warp handle caching, pointer-move resync, the recapture token, the warm-up carry
  list and the reset-mask stamp. **Zero opt-outs** — a test asserts all 10 implement the same
  four members and override none of the framework's. `swarp/core/hooks.py` holds
  `WholeStepHook`, the declared form of what the scenario hands `StepRuntime`. Contract and
  capture-safety rules: `docs/writing-a-scenario.md`.

## Design Invariants (read before extending the step)

- **The step is functional** (`state_in → state_out`). Every array written during a taped step
  (intermediate states, force buffers, neighbor lists) must be allocated **fresh per step** —
  overwriting an array recorded on a `wp.Tape` silently corrupts its adjoint. `Stepper` is the
  single place that knows this; the no-grad hot path recycles one cached `StepBuffers` per batch size.
- **Precision is explicit.** Kernels are generic over dtype and instantiated for float32/float64
  via `wp.overload` (see the `_signature(dtype)` helpers in `kernels.py`/`collisions.py`).
  float64-on-CPU is what makes strict `torch.autograd.gradcheck` possible.
- **Collision forces are gather-based** — each agent sums over its own neighbor list. No atomics:
  deterministic and race-free.
- **Neighbor construction is not taped** (`record_tape=False`); the neighbor *set* is discrete, so
  gradients flow through contact geometry, not through membership.
- `wp.HashGrid` wraps cell coordinates modulo its dims, which aliases cells across the z-lifted
  env batching — brute force wins up to a few hundred agents/env.

## Code Style
